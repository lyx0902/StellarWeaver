# 文件改动、启动基线与撤销

StellarWeaver 的改动管理围绕会话 journal 和内置文件工具工作。它保存启动时的 Git 证据，并对每次内置修改保存独立的 before 快照、before/after SHA-256、路径和文件权限。数据库和制品位于会话数据目录；凭据文件不进入基线或补丁展示。

## 启动基线

首次任务开始前，程序采集并记录 `changes.baseline`：

- Git 的 staged、unstaged、untracked 路径；
- 允许访问的已变化文件的当前 hash、长度、权限和类型；
- 启动时的 staged diff 和 unstaged diff。

这些都是用户基线。采集不执行提交、暂存、重置、清理或整仓 checkout，也不修改 Git index。已有脏文件仍可由内置工具按 hash 编辑；该次编辑的 before 快照保留的是编辑前的用户内容。

采集尊重保护路径和忽略规则。`.env`、私钥、会话数据库等不读取内容。单个基线文件超过 8 MiB 时不计算内容 hash；Git 输出被截断时记录限制，不声称证据完整。不是 Git 仓库或 Git 不可用时，仍支持有完整 journal 的内置修改与撤销，但不能完整分类 shell 等外部变化。

基线或 `/diff` 的 Git 子进程被取消、清理状态为 unknown，或进程隔离启动失败时，先记录 `changes.observation_unknown` 及原始进程管理证据，再停止当前观察；任务启动阶段不会继续调用模型，也不会把这种状态降级为普通的无 Git 环境。

旧会话如果没有启动基线，第一次查看时会明确标记 `after_recorded_operations`。这是事后快照，不能用于断言启动前的真实状态。

## `/diff` 的三个来源

在 `chat` 中输入 `/diff`，显示：

1. **用户启动基线**：当时的 staged/unstaged/untracked 状态及已记录补丁。
2. **Agent 内置文件改动**：尚未撤销的 `create_file`、`edit_file` 操作、操作 ID、路径和精确补丁。
3. **其他当前变化**：当前 Git 状态与已知基线、内置 after hash 不一致的路径，以及启动后发生的 staged diff 变化。

核对路径取启动基线、当前 Git 路径和内置修改路径的并集。即使 Git 已不再列出该路径，也会实际观察它：启动时 untracked 文件消失、脏 tracked 文件被还原为 Git clean、原本删除的 tracked 文件重新出现，以及文件类型变化都会保留在报告中。Git 明确报告的 rename 同时保留旧路径和新路径；程序不会凭相似内容猜测未跟踪文件的重命名来源。每条额外变化附上基线与当前观察。当前 bytes、权限和类型完全恢复至原用户基线时，不误报为新的内容变化。

这里的来源分类依赖已保存证据。它不会把 shell、测试、格式化器、用户编辑器或 MCP 所产生的变化自动算成内置编辑，也不能只凭 Git diff 推断某个外部变更是谁写的。

## `/undo`：逆序、单步、重新授权

在 `chat` 中输入 `/undo`，每次处理最近一条尚未撤销的内置文件修改。连续调用按记录逆序逐步回退；每一步独立完成，不是跨文件事务。

撤销前必须同时满足：

- 原操作有明确成功结果和完整路径、hash、权限元数据；
- 路径仍在固定工作区内，没有改成符号链接或其他文件类型；
- 当前文件 hash 仍等于该操作记录的 after hash；
- 当前权限仍与记录匹配；
- 编辑操作的 before 快照仍在本会话制品目录内，且内容 hash 与原 before hash 匹配。

编辑满足条件时，从 before bytes 原子恢复并保留原权限。新建满足条件时，只删除该次操作创建的文件。程序不清理其他文件或目录。

`/undo` 使用当前策略重新判断写权限。授权预览带有 `action=undo`、原操作 ID 和反向补丁。无交互终端且没有相应写授权时返回 blocked；只读模式拒绝撤销。等待授权后还会再次检查 hash、路径、权限和快照，防止授权窗口期间覆盖用户新编辑。

用户在 Agent 修改后又编辑了文件、改了权限或改坏了快照时，撤销被拒绝并保留现状。当前协议不能把这些冲突自动合并成一次安全回退。

对一个原本就有 staged、unstaged、untracked 内容的仓库，撤销只恢复对应操作保存的 before 内容。它不读取旧 Git 版本来覆盖工作区，也不触碰 index，因此不会用仓库历史替代用户的启动基线。

## 执行证据与中断

写动作在模型已见的适用 `AGENTS.md` 上下文内准备。授权返回后，独立的 `after_authorize` 检查再次比较适用指令的路径与 hash；新增、修改或删除会得到结构化 `INSTRUCTIONS_UPDATED`，在 `tool.started` 和文件写入之前停止。原有 `before_execute` 回调不重复调用，文件自身的 hash/权限复检仍随后执行；读取工具不会因此获得额外写权限。

内置编辑先耐久保存 before bytes 和 diff，再写同目录临时文件、同步并原子替换。新建使用排他创建。POSIX 支持时同步目录项；Windows 的目录同步能力有限，不能据此承诺任意断电情况下的持久性。

撤销有独立的 `changes.undo.authorization`、`changes.undo.started` 和 `changes.undo.completed` 事件。开始事件在文件变化前提交，完成事件在实际变化后提交，UI 只在持久化后发布。

如果撤销已修改文件、完成事件尚未提交就退出，`resume` 或再次 `/undo` 首先核对目标状态：内容 hash 和权限均符合恢复后状态（或该次新建文件已不存在）时，仅补记从状态恢复的完成结果，不再次应用。

观察不到撤销效果、发现内容冲突、权限改变或无法安全读取时，保留文件，记录明确的 blocked/unknown 结果并要求处理。连续不带新任务的 `resume` 仍保持 `requires_attention`，不会因结果已经写入而放行。显式新任务可以接手当前状态，但不会重放旧撤销。一个新的、获授权的撤销成功后，对应目标的旧撤销待处理状态才可解除。

普通内置编辑的中断由会话恢复协调 before/after hash；`run_command` started 后没有结果时标为 unknown，不自动重跑。未知结果不会被当作可安全撤销的内置成功修改。

## 范围与并发

`/undo` 不保证撤销 shell、测试、格式化器或外部 MCP 的变化；这些变化需要结合 `/diff`、Git 和真实文件状态检查。没有 `git reset --hard`、`git clean -fd` 或整仓 checkout 回退路径。

工作区写锁按规范化绝对路径生成独立身份，使用操作系统文件锁在不同会话和进程之间互斥。内置修改、命令和可写 MCP 调用在准备、授权、执行与结果提交期间持有锁；另一 Agent 写者得到明确的 `WORKSPACE_BUSY`。会话自身另有独立的单写者锁。

这些锁约束的是配合协议的 StellarWeaver 进程。用户编辑器和其他程序不会受此锁约束；hash 检查和原子替换也不是面向任意外部并发写者的全局 CAS。工作区写锁不是操作系统沙箱。

## 已执行验证

本轮自动测试覆盖脏 Git 基线、基线路径从 Git 状态消失、rename 和类型变化、恢复用户基线不误报、两次逆序撤销、保持 index bytes、删除内置新建文件、用户后续内容/权限/快照冲突、授权等待期间文件及根/子目录指令变化、无 TTY 拒绝、无 Git 的明确降级、真实进程写锁，以及撤销写入后进程退出的状态恢复。真实内置编辑中断及继续测试见 `tests/integration/test_m3_recovery.py`。
